# Smart Library 设计规范（v0.3）

技术路线：Tauri 2 + Rust + Tantivy + SQLite，仅桌面端。
本文由设计会话整理而成，是代码仓库中的唯一规范来源（会话中的 Claude Doc 草案 v0.1 已并入此处并修正）。
标注「待确认」的内容是尚未用数据验证的假设。

## 0. 摘要：只有三个核心抽象

- **统一节点（Node）**：藏经的一卷、Wikipedia 的一篇文章、一个文件、一条笔记，结构完全相同：有名称、有父级，可能有内容，可能有子级。差别只在于有没有内容、有没有子级。
- **仓库适配器（Adapter）**：把任意数据源（zip、目录、Wikipedia 包、自维护库）统一成这种节点树，按需提供子节点、内容和可索引文本。
- **定位器（Locator）**：搜索命中后如何回到具体位置，由适配器自己定义和解释，核心与界面只负责传递，不关心内部格式。

各数据源专属的阅读功能（卷的同级导航、经内大纲、校勘注释）不进入节点模型，由适配器以**可选扩展**提供（见第 9 节）。目录树、全文搜索、标题快搜、导出、阅读，都是这三者的组合；新增一种数据源，只需要多写一个适配器。

## 1. 目标与非目标

**目标**

- 把多种来源的资料组织在同一棵目录树下，统一浏览、统一搜索。
- 搜索是核心体验：精确、快速、可限定范围、可分面、可导出、可定位。
- 启动快、安装包小、不依赖外部服务（不装 JVM、不起 Solr）。
- 只读仓库永不修改源数据；自维护仓库可读写。

**非目标（初期）**：手机端、多人协作与云同步、修改 Obsidian 等外部库的数据、通用富文本或排版编辑器。

## 2. 术语

- **知识库（Library）**：目录树里的每个根节点就是一个知识库（目录树没有唯一的总根）；反过来，知识库只出现在根节点这一层。它是绑定、建索引、限定搜索和快搜范围的单位。一个数据包可以提供多个知识库（bookcase 的 CBETA 一棵树加各自加树，见 9a）。
- **仓库（Repository）**：一个数据源，由一个适配器负责读取；它向目录树提供一个或多个知识库。
- **节点（Node）**：目录树中的一项，也是阅读和检索的基本单位。有没有内容、有没有子级是两个独立属性。
- **内容节点**：有内容的节点。全文索引只针对内容节点，标题快搜针对所有节点。
- **范围（Scope）**：用户在目录树中勾选的一个或多个节点，用于限定搜索。
- **命中（Hit）**：一次搜索结果，包含节点、摘要和定位器。

## 3. 总体架构

自上而下四层：

1. **界面层**：Tauri 窗口。左侧目录树，右侧单个 Webview 内容区，另有搜索面板和标题快搜浮层。前端用 Vue 或 Svelte，Node 只在开发时使用。
2. **命令层**：Tauri 的 commands 与 events，只做参数转换，返回 JSON，不含业务逻辑。
3. **核心库 core**（纯 Rust，不依赖界面）：仓库管理器、适配器接口及实现、索引器、搜索服务、标题索引、后台任务队列。
4. **存储层**：SQLite（注册表、设置、笔记）、Tantivy 索引目录、各数据源本身。

工程组织为 Cargo workspace：`core`（库）、`cli`（命令行，开发期验证）、`app`（Tauri，之后加入）。**先让 core 加 cli 跑通，再接界面**，这样每一步都能独立测试。

## 4. 节点模型

**节点 ID**：全局唯一，形如 `仓库ID:本地ID`。本地 ID 由适配器决定，但必须稳定（数据更新后不变）。例如 CBETA 用经号和卷号，文件系统仓库用相对路径，笔记库用 UUID。

**节点字段（草案）**

- `id`、`parent_id`、`position`（同级排序）
- `name`：标题；`aliases`：别名列表（异名、简称、译名等），参与标题快搜
- `description`：简短说明或摘要
- `contributors`：作者、译者、编者等，每项含姓名和角色
- `attributes`：键值对，存放各数据源的专属信息（朝代、册号、原书页码、标签、创建时间等）
- `content_type`：内容类型（HTML、Markdown、纯文本、PDF、媒体等），无内容时为空
- `has_content`、`has_children`：由适配器按需给出，不必为了判断而加载全部内容或全部子节点
- `content`：正文本身。只读仓库不在节点里存放，通过 `content(id)` 按需读取；自维护库存放在 SQLite 中

**不区分卷、文章、文件、笔记**：它们是同一种节点。有子级时，目录树把它显示为文件夹；无内容时，在 Webview 中打开为空白（可写仓库可直接开始编辑）或不允许打开（只读仓库）；既有内容又有子级时两者兼有（Everything is a Note，借鉴 Trilium）。节点上没有 `kind` 字段，图标等展示需求由 `content_type` 和是否有子级推出。

**索引粒度由此自然得出**：全文索引针对所有有内容的节点。CBETA 里只有「卷」有内容，「经」只是带元数据的目录节点，所以按卷索引；本地目录里每个文件是一个内容节点。粒度完全取决于适配器让哪些节点有内容。

**懒加载**：目录树按需展开，`children(parent)` 每次只返回一层。Wikipedia 这类百万级节点的仓库不可能一次构建整棵树。

**多棵树**：一个仓库可以提供多种组织方式。例如 CBETA 官方的 bookcase.zip 里有 3 棵目录树（用户的数据包可以另加，见附录 A.3），适配器通过 `trees()` 暴露它们，用户设置默认使用哪一棵。

## 5. 适配器接口（草案）

```rust
trait Repository {
    fn info(&self) -> RepoInfo;                    // 名称、类型、能力声明
    fn trees(&self) -> Vec<TreeInfo>;              // 可用目录树，至少一棵
    fn children(&self, tree: &TreeId, parent: Option<&NodeId>) -> Result<Vec<Node>>;
    fn node(&self, id: &NodeId) -> Result<Node>;
    fn content(&self, id: &NodeId, opts: &RenderOpts) -> Result<Content>;
    fn index_nodes(&self) -> Box<dyn Iterator<Item = Result<IndexNode>> + '_>;  // 有内容的节点，供建索引
    fn fingerprint(&self) -> Result<String>;       // 数据版本指纹，变化则提示重建
    fn locate(&self, node: &NodeId, q: &ParsedQuery) -> Result<Vec<Hit>>;     // 节点内命中位置
    fn cite(&self, hit: &Hit) -> String;           // 导出用的引用文本

    // 可选扩展，默认实现返回空
    fn outline(&self, id: &NodeId) -> Result<Vec<OutlineItem>> { Ok(vec![]) }  // 节点内标题大纲
    fn view_options(&self) -> Vec<ViewOption> { vec![] }                       // 阅读选项：简繁、分行、注释
}

trait Writable: Repository {
    fn create(&self, parent: Option<&NodeId>, draft: NodeDraft) -> Result<Node>;
    fn update(&self, id: &NodeId, patch: NodePatch) -> Result<()>;
    fn delete(&self, id: &NodeId) -> Result<()>;
    fn move_to(&self, id: &NodeId, new_parent: Option<&NodeId>, pos: usize) -> Result<()>;
}
```

要点：

- 适配器**不依赖 Tantivy**，只负责提供数据和位置。索引器、搜索服务是独立模块。
- `IndexNode` 包含：节点 ID、名称、别名、纯文本正文、贡献者、属性、分面路径列表、语言。
- `Content` 的类型：HTML、Markdown、原始文件（PDF、图片、音视频）、无内容。
- 只读仓库只实现 `Repository`，可写仓库再实现 `Writable`，界面按能力决定是否显示编辑入口。
- 可选扩展有默认实现，界面据此决定是否显示对应的面板。

## 6. 各类仓库的适配要点

### 6.1 CBETA（bookcase.zip，只读）

- 用 `zip` crate 随机读取，不解压，更新时直接替换 zip。数据源格式见附录 A。
- 节点：册、部类等为目录节点；「经」是带元数据（作译者、朝代、典类）的目录节点；「卷」是有内容的节点，也是唯一被全文索引的节点，所以索引粒度为卷。
- 数据装配：`bookcase.zip` 不能直接遍历 XML 使用，要先把 `catalog.txt`、`bookdata.txt`、三棵 `*_nav.xhtml` 和每部经的 `toc` 文件串起来（附录 A.2–A.4）。适配器启动时装配成内存中的目录与元数据表，并按 zip 指纹缓存，卷 XML 本身仍按需随机读取。
- 元数据与分面：典类、人物、时域来自人工整理的 `data/bookinfo.json`（附录 A.5）。
- 卷内定位：打开或展示结果时，实时解析该卷 XML，得到「纯文本 + 偏移量到原书行号的映射」，扫描所有命中偏移，再转成行号。不保存任何衍生数据。
- 阅读扩展：同一部经的各卷导航由目录树得出；经内标题大纲用 `outline`（数据来自 toc 文件）；简繁切换、原书分行、校勘与注释的显示用 `view_options`。
- 指纹：zip 的大小与修改时间，加 `index.xml` 的版本与日期。
- 简繁、异体字、缺字的归一化在统一的归一化管线中处理，原文保持不动。
- 使用前需核对 CBETA 的授权条款。

### 6.2 本地目录（资料目录、Obsidian 库，只读）

- 子节点即真实目录与文件；每个文件是一个有内容的节点。
- 文本和 Markdown 直接读取；PDF、docx、epub 等需要文本提取（依赖库待评估）；媒体文件提取时长、编码、标签等元数据后建索引。
- Obsidian 库按 Markdown 目录处理，可额外解析 frontmatter、标签和双向链接作为元数据，全程只读。
- 变更检测：比较路径、修改时间、大小，做增量索引；文件监视作为可选功能。

### 6.3 Wikipedia 离线包（只读，后期，需先调研）

- 据我所知，常见的离线形式是 Kiwix 的 ZIM 文件：可随机读取，内含压缩的 HTML 文章和标题索引。这一点需要确认实际使用的是哪种包。
- 它本质上更像「按标题排列的扁平文章集合」，不是真正的目录树。树可能要虚拟构造（首字母、分类等）。
- 几十 GB 的规模下，建索引的耗时和体积需要实测，可能需要「只索引标题」或「只索引摘要」的降级模式。

### 6.4 自维护知识库（读写）

- 存储：SQLite。核心表 `notes`：`id`、`parent_id`、`title`、`content`、`content_type`、`position`、`created`、`updated`、`attributes`。树由 `parent_id` 和 `position` 构成。
- 内容格式：建议以 Markdown 为主，保持简单、可导出、可检索。
- 写入流程：先写 SQLite 事务，成功后向索引器发出变更；索引器合并变更，约每秒批量提交一次。**以 SQLite 为准，索引随时可以重建。**
- 初期不做 Trilium 的「克隆」（一个节点挂在多个父节点下），以降低复杂度。
- 「我的日记」是同一种适配器的另一个实例，不需要单独实现。

## 7. 索引设计

**每个仓库一个独立的 Tantivy 索引目录**，不做一个全局大索引。理由：

- 各仓库规模差异极大（藏经几百 MB，Wikipedia 几十 GB），独立索引便于单独重建和删除。
- 各仓库可以有不同的分词与归一化策略。
- 导入或移除仓库互不影响。

**通用字段**：`node_id`、`name`、`aliases`、`body`（只索引，不存储）、`contributors`、`path`（层级分面）、`lang`，以及各仓库自定义的属性字段（朝代、册号等）。只有内容节点进入全文索引。

**默认分词器 `aio`，所有仓库共用**：沿用 cbeta-explorer 在 Solr 中验证过的 `text_aio` 组合，即标准分词（拉丁文按词，汉字逐字）、全半角折叠、小写、CJK 二字组。混合文字实测没有问题，所以各仓库默认共用，需要时再单独覆盖。

对旧 Solr 实现的实测结果（用 cbeta-explorer 验证）：

- 单字查询可以命中（旧界面搜「念」得到 904 条结果），所以新分词器必须支持单字。旧界面的文档粒度看来是章节（结果标题是『念』这样的章节名），与新实现的「卷」不同，条数不可比：新索引里含「念」的卷有 18407 个。
- 默认查询是**宽松匹配**：各二字组出现在同一内容节点内即可命中，不要求相邻（见 8.3）。

**M0c 的实现**（`core/src/analyzer.rs`、`core/src/search.rs`）：

- 字符折叠：NFKC（全半角、兼容汉字）、小写、**繁体到简体**（`data/t2s.txt`，2734 对，一字对一字，取自 fast2s，MIT）。索引和查询、命中定位三处用同一个折叠函数，原文不变。代价：少数不同的繁体字会合并（乾、幹都到「干」，於到「于」），对宽松检索可以接受。异体字表以后再加。
- 字符分类：CJK（汉字各区、假名、谚文、PUA 缺字、〇 々 〡）连成一段；标点和空白是**透明**的，不打断汉字段（二字组跨逗号，与卷的 `plain` 一致），但会结束拉丁词；其他符号（○ △ ─ 等）打断汉字段；字母数字连成一个词。
- 两个字段：`body` 放二字组、拉丁词和单字段（长度为 1 的汉字段），**带位置**，用于短语；`body1` 放所有单字，**只有词频没有位置**，因为单字查询永远不需要位置。这样单字不必付出位置信息的体积。
- 一卷一个文档，索引的是带标点的 `text`（标点透明，空白仍能分开拉丁词）。另有 `path`、`book`、`juan`、`title` 存储字段和一个 `facet` 字段。
- 2025.Q1 实测：21233 卷（LC、Y 不收），建索引约 43 秒，索引 761 MB；单字「念」搜索 25 ms，短语「如是我聞」8 ms；命中定位每卷约 1–3 ms。
- 索引目录默认 `app_data/repos/cbeta/index`，里面的 `smart-library-index.json` 记录索引版本（`INDEX_VERSION`，分词器或字段变化时加一）和数据版本；版本不符时要求删除重建。

Tantivy 的实现要点（设计时的预估，已按上面实现）：

- Tantivy 没有现成的 CJK 二字组过滤器，也没有 UAX#29 标准分词器，需要实现一个自定义分词器（预计一两百行 Rust）：拉丁文按词切分并转小写，汉字连续段输出单字和二字组，并给每个词元正确的位置，因为短语查询依赖位置。可借助 `unicode-segmentation` 判断词边界，用 `unicode-normalization` 的 NFKC 完成全半角折叠。
- Solr 里的同义词过滤器（`SynonymGraphFilter`）在 Tantivy 中没有现成实现，改在查询构建层做：把词展开成 OR 组。
- Lucene 与 Tantivy 的性能差异（Lucene 平均约快 1.5 倍，均为亚毫秒到毫秒级）对本项目规模无实际影响，选型依据是语言、体积和启动速度。

**归一化管线**（繁简、异体字、标点）在索引和查询两侧必须使用同一套。字级别的繁简和异体字映射建议放在索引侧，原文保持不动；查询侧的同义词展开只用于词级别，因为字级别展开会让 N 个字的查询膨胀成各变体的乘积。

**标点**：古籍用户输入的短语通常不带标点，索引时忽略标点，并保留位置映射，这样跨逗号的短语也能命中。CBETA 的标点是后加的一层（附录 A.6），去掉标点后偏移与原书行内位置一致。

**索引更新**

- 只读仓库：导入时全量建索引；`fingerprint` 变化时提示重建；目录类仓库支持增量。
- 自维护仓库：随写入实时增量更新。
- 所有索引任务进入**后台任务队列**：有进度事件、可取消、可断点续建，界面不能被阻塞。

## 8. 搜索

**8.1 范围限定**

用户在目录树中勾选一个或多个节点，系统把它们解析为「仓库 → 过滤条件」。过滤基于文档的 `path` 层级分面（例如 `/藏经/大正藏/阿含部`），按前缀匹配。一个文档可带多个 path，以兼容仓库的多棵目录树。

**8.2 跨仓库排序**

不同索引的 BM25 分数不可直接比较（统计基数不同）。默认**按仓库分组展示**，组内按分数排序；需要混排时，用 RRF 之类只看名次的融合方法。

**8.3 匹配模式**

- **宽松匹配（默认）**：把查询切成二字组，**要求全部词元**出现在同一个内容节点内，不要求相邻，按 BM25 排序，适合只记得大概的用户。cbeta-explorer 的设计理念就是不要求输入与原文完全一致的字句。已用旧截图验证：「他念摄之令常在像」只命中《坐禪三昧經》卷一，片段分散，与旧界面一致。
- **查询里的空格分隔关键词**：宽松匹配时 `比丘 他念` 是两个关键词，不产生跨空格的二字组「丘他」；精确短语忽略空格。文档里的空白则始终透明。
- **精确短语**：要求词元按顺序相邻，依赖位置信息。
- 另有邻近（A 与 B 相隔 N 字内）、排除词、字段限定，正则放到后期。

**8.4 结果与分面**

命中包含节点、路径、摘要片段和定位器，另附分面计数（按部类、朝代、作译者等）。**计数单位：分面计数是命中卷数**；总数同时给出命中卷数和命中经数（经数来自 `/book/经号` 分面的子项个数）。每卷的出现次数在定位时得到。

M0c 的分面根：`/bulei/部類/子類`（层级）、`/canon/藏经代码`、`/kind/典类`（「论：经释」拆成两级）、`/period/朝代`、`/person/人物`，后三者来自 `data/bookinfo.json`（已嵌入程序）；表里没有的经暂时没有这三项。范围限定用同一套分面，如 `bulei/阿含部類`。注意父级计数可以大于子级之和：有的经只有部類没有子類（如 F 藏）。

分面按多个维度并列显示（部类、时域、人物、藏经、典类），每个维度可以是层级的，父级计数等于各子级之和（旧界面中阿含部类 43 = 36 + 1 + 6）。每条结果显示标题、路径、贡献者，以及若干条带高亮的上下文片段，每条片段附「转到」入口。参考截图见 `docs/reference/`。

**8.5 定位**

引擎返回命中的文档和排序后，只对**当前页**的结果调用适配器的 `locate`，得到节点内所有命中位置。定位器格式由适配器定义（CBETA 是行号加行内位置，Markdown 是标题加字符偏移，PDF 是页码），核心只负责传递。旧实现用 Solr 高亮返回文本片段，点击后靠文字回找位置，重复句无法区分；新做法返回位置，每一处命中都有独立的行号。

**8.6 导出**

支持 Markdown、CSV、JSON。每条结果的引用文本由适配器的 `cite` 生成（例如「T08n0223，卷 1，0003b12」）。

**8.7 标题快搜（双击 Shift）**

独立于全文索引。启动时把节点标题、别名、作译者等载入内存，输入即响应，毫秒级。仓库过大时（如 Wikipedia 标题）改用磁盘上的 FST，通过内存映射访问。简繁不敏感，拼音首字母作为可选功能。

M2 的实现（`core/src/titles.rs`，命令行 `titles`，界面 `app/src/lib/QuickSearch.svelte`）：

- 条目（每个知识库一份，第一次用时建立，程序启动后在后台预先建立）：
  - CBETA：所绑定目录树里的每部经（按树的顺序；`T0220a` 这类大经的一段是单独的经条目，打开它自己的起点），接着是这部经 toc 的目次（序、品、分、经…，跳到锚点行）和卷（只有一卷的经不列卷）。toc 里指向不存在文件的目次不列。
  - HTML 知识库：每篇文章，所在文件夹作为上下文。
  - 一部经的经号、经名、作译者（或文章的文件夹）只存一份，供该经所有条目共用。文件夹本身暂不作为条目。
- 匹配：查询按空格切成关键词，每个关键词都要出现在条目标题或它所属的经（经号、经名、作译者）、文件夹里。比较前用分词器的 `match_key` 折叠（NFKC、小写、繁转简，去掉标点和空白），所以简繁、全半角、标点都不敏感。
- 排序：标题以第一个关键词开头 > 关键词都在标题里 > 有关键词只出现在上下文；同一档内经和文章在前、目次其次、卷最后，再按标题与查询完全相同、标题短者在前；仍相同则保持目录树顺序。目次标题开头的序号（「1 序品」的「1」）不参与排序判断。
- 不分库（「全部」）时，各库的结果按上述排序合并，名次相同时按知识库的顺序；同时返回每个库的命中数。最多显示 200 条，另给总数。
- 实测 2025.Q1：部類目錄 317446 条，建立约 0.7 秒（release）；查询 4–8 ms。乾隆大藏经 8095 条、索达吉堪布全集 5242 条，各约 0.1 秒。
- **`#` 命令与 CBETA 引用**（`core/src/cite.rs`，CBETA 专用，沿用 cbeta-explorer 的做法）：查询以 `#` 开头时不搜标题，只按命令转到经、卷或行，结果是一条「转到 »」（不管选的是哪个知识库标签，定位用已绑定的 CBETA 知识库）。只输入 `#` 或格式不对时，弹窗列出格式说明。

  | 命令 | 转到 |
  | --- | --- |
  | `#T01n0001_p0001a01` | T0001（第 01 册）的 0001a01 行 |
  | `#T0001_p0001a01` | T0001 的 0001a01 行 |
  | `#T01, no. 1, p. 1a1` | T0001 的 0001a01 行（引用格式；也接受旧式 `p. 1, a1`、范围 `pp. 1a1-2b3` 取起点） |
  | `#T01n0001_1`、`#T01n0001_001` | T0001 的第 1 卷 |
  | `#T0001_1`、`#T0001_001` | T0001 的第 1 卷 |
  | `#T0001` | T0001（打开第一卷） |

  - 经号忽略前导零（`T1` 即 `T0001`，`JB480` 即 J 藏的 `B480`）；`T0220a` 这类目录里的分段在 catalog 里没有，去掉字母按 `T0220` 找。
  - 只给行时，卷是：起始行（`spine.txt`）不晚于该行的卷文件，而下一个卷文件的起始行晚于该行（或者页码重新开始，即进入下一册）；给了册号时只在这一册里找。
  - **粘贴引用**：粘贴 CBETA「复制为引用」的文字，如 `《坐禪三昧經》卷1：「第五法門……」(CBETA 2025.Q1, T15, no. 614, p. 269c29)`，输入框自动换成对应的命令 `#T15, no. 614, p. 269c29`，引文另外保留。不以 `#` 开头的查询里含有引用（`T15, no. 614, p. 269c29` 或行首 `T15n0614_p0269c29`）时，也在标题结果前面给出「转到 »」。`// Z 2B:8, p. 298` 这类其他版本对照不识别。
  - 引用行不一定是引文所在（上例写的是卷首 269c29，引文在 276a07）。有引文时，在这一卷里按精确短语找它（忽略标点、简繁折叠），找到就跳到不早于引用行的第一处（没有则第一处），打开时引文高亮。
  - 找不到经、卷或行时显示一条红色的提示。
- 界面：双击 Shift（两次之间没有别的键，400 ms 内）或顶部「快搜」按钮打开弹窗。上方标签是「全部」和各知识库（带命中数，Tab / Shift+Tab 切换，只能单选）；输入即搜；↑↓、PageUp/PageDown 选择，Enter 或单击打开（经打开第一卷，目次跳到对应行），Esc 或点外面关闭。每行左侧是类型（经、目、卷、文），然后是标题、所属经或文件夹、作译者，「全部」时右侧显示知识库。上次的查询和所选知识库保留到下次打开。

## 9. 内容展示与视图扩展

- 右侧只有**一个 Webview**，通过 Tauri 自定义协议（如 `smart-library://仓库/节点`）取内容，前端不直接访问文件系统。
- 适配器返回内容类型：HTML 片段、Markdown、原始文件（PDF、图片、音视频交给 Webview 原生处理）。
- 阅读选项（CBETA 的简繁切换、原书分行、注释显示方式）是 `content` 的参数，由适配器解释。
- 安全：来自 Wikipedia、Markdown 等的 HTML 一律消毒、禁止脚本，外部链接用系统浏览器打开。
- 命中高亮：前端拿到定位器后滚动并高亮，不依赖文字匹配。

**视图扩展：各数据源的专属功能**

专属的阅读功能不放进通用节点模型。适配器以可选扩展的方式提供，界面按能力声明决定显示哪些面板：

- **同级与上下级导航**：由目录树本身得出（`children`、`parent`），无需扩展。CBETA 的卷页因此自动获得同一部经的各卷列表。
- **节点内大纲（`outline`）**：返回节点内的标题层级，用于快速定位跳转。CBETA 是经内的品、章，Markdown 是标题，Wikipedia 是文章章节，PDF 是书签。这是通用扩展，多数仓库都能提供。
- **阅读选项（`view_options`）**：适配器声明可切换项，界面画成工具栏，选择结果作为参数传给 `content`。
- **专属渲染**：校勘注释等需要特殊交互的部分，由适配器在 HTML 中输出带语义的标记（如 `data-` 属性），再由随仓库类型加载的一小段前端脚本处理，不污染通用前端。

## 9a. 多标签阅读与知识库绑定

用户在 M1 之后提出，排在结构化阅读之后实现。两部分都已完成。

**多标签页**

- 阅读区支持多个标签页，一个文档只开一个标签页：再次打开同一文档时切到已有标签并跳到目标位置。
- 标签页可以**停靠**（左右、上下分栏，拖动标签到另一组）和**浮动**，用于多部经对照。
- 阅读进度要记录并还原：每个文档的当前卷、滚动位置（以屏幕顶部的行号 `lb` 记录，不用像素）、版式（段落或原书行）；程序重启后还原打开的标签页和布局。
- **用户已定：一卷一个标签；浮动既要窗口内浮动面板，也要独立系统窗口。**
- 实现（`app/src/lib/workspace.svelte.js`）：
  - dockview-core 8（MIT）。它的 ES 模块不带样式，样式从 UMD 版抽出放在 `app/src/vendor/dockview.css`，升级时要重新抽取。
  - 标签 id 就是卷路径。打开一卷时：已在独立窗口中就把那个窗口提到前面并跳转；已在标签中就激活并跳转；否则在当前组新开。卷选择和跨卷的目次跳转同样走这条规则（同一卷内的目次只滚动）。
  - 标签右键菜单：关闭、关闭其他标签、向右分栏、向下分栏、浮动（窗口内，默认占工作区约一半）、停靠回主区、在新窗口打开。也可以把标签拖到边缘停靠（拖动由 dockview 处理）。
  - 搜索结果也是一个标签（`search`），可以和阅读标签并排；它不保存。
  - 独立窗口是 Tauri 的 `WebviewWindow`（标签名 `reader-<路径>`，URL 带 `?popout=` 参数），只显示一卷，标题栏有「停靠回主窗口」。它不写文件，用事件 `popout-progress`、`popout-closed`、`popout-dock`、`popout-open` 通知主窗口；主窗口用 `popout-jump` 让它跳转。用户关窗口才算关闭，程序退出时不算，所以重启后会重新打开。
  - 进度：每卷记录屏幕顶部的行号 `lb` 和版式（滚动停止 0.4 秒后），最多 500 卷，关掉标签也保留，再打开同一卷时安静地回到原处（不闪烁标记）；搜索命中的跳转优先。
  - 保存：布局（`toJSON`）、独立窗口列表、进度、默认版式一起写进应用数据目录的 `workspace.json`（Tauri 命令 `load_workspace`、`save_workspace`，先写临时文件再改名），改动后 0.8 秒保存。启动时打开 bookcase 后还原。
  - 在程序里验证过：向右分栏对照两部经、同一卷再次打开只激活、浮动与停靠回主区、弹出窗口与停靠回主窗口、彻底重启后标签、滚动位置和弹出窗口都还原。
  - 切换标签时保留阅读位置：dockview 会把隐藏标签的元素移出页面，滚动位置随之归零；每个阅读标签记住自己的滚动位置，重新显示时放回（内容并不重新载入）。
  - 在目录树中定位：标签右键「在目录树中定位」或阅读区标题栏的 ⌖ 按钮，展开目录树直到这部经（大经分段时取起点不晚于当前卷的那一段）或这篇文章，选中并滚动到可见处。目录树的展开状态因此由知识库面板统一保存（节点键是下标路径 `/0/3/5`）。
  - 左侧目录区宽度可拖动分隔条调整（最小 180 像素，最大窗口的 70%，键盘左右键每次 20 像素，双击还原 300），保存在前端本地。
  - 已知：用自动化工具模拟的拖动没有触发 WebView2 的原生拖放，所以拖动停靠只能手动验证；规范第 10 节的 `registry.db` 建好后，`workspace.json` 再迁移进去。

**知识库绑定**

- 程序启动后，在左侧目录树上右键「绑定知识库…」，选择数据源（如 CBETA 的 bookcase.zip）；可以绑定多个，每个绑定成为目录树的一个根节点。
- 绑定 bookcase 时解析 `menu_nav.xhtml`，列出其中的目录树让用户选择：
  - CBETA 自带的三棵树（簡易、進階、部類）**数据是同一份**，只能选一棵，默认 `bulei_nav.xhtml`。以后可以换成另一棵，因为索引按数据建，换树不需要重建索引。
  - 用户自加的树（如 `zhibei` 索达吉堪布全集、`longzang` 乾隆大藏经）数据各不相同，可以同时绑定，各自一个独立索引（规范第 7 节：每个仓库一个索引）。
- 判断两棵树是否「同一份数据」不写死文件名，而是看叶子指向：指向 `XML/` 的属于 CBETA 主数据，指向 `a/<库名>/` 的属于该库（`a/ZB/`、`a/LZ/`）；`help/` 等说明页不计。
- 依赖：自加树的内容是 `a/` 下的 HTML，需要先把它们接入为内容节点（抽取正文、建索引、阅读），见下面「HTML 文章」。

**知识库绑定的实现**

- core：`library.rs` 的 `classify_trees` 按叶子指向判断每棵树（`Cbeta`、`Html(代码)`、`Other`），实测 2025.Q1：簡易、進階、部類为 CBETA；`zhibei` 为 `a/ZB/`，`longzang` 为 `a/LZ/`。`HtmlTree` 从树里得到文章（含所在文件夹链和同级文章），并产生索引文档；`cbeta_docs` 产生 CBETA 的索引文档。`search::build_index` 只接收这些普通文档，适配器仍不依赖 Tantivy。
- 注册表：`<应用配置目录>/libraries.json`，每个知识库有 `id`（`cbeta`、`zb`、`lz`，重名加 `-2`）、`kind`（`cbeta` 或 `html`）、`title`、`source`（数据包路径）、`tree`。索引在 `<应用数据目录>/repos/<id>/index`。第一次启动时，旧版的单一 bookcase 设置自动迁移为 `cbeta`（部類），沿用原来的索引。
- 界面：左侧每个知识库是一个根节点，展开时才载入目录；「＋ 绑定」或在空白处右键「绑定知识库…」打开绑定对话框：选择文件或文件夹（系统对话框），读取后列出 CBETA 三棵树（单选，默认部類，已绑定的标「当前绑定」）和其他知识库（多选，已绑定的不可再选）。知识库右键菜单：展开、建立或重建索引、更换目录树（CBETA）、从同一数据包绑定其他知识库、解除绑定（系统确认框；删除该库的索引和标签，数据包不受影响）。根节点上显示「未建索引」「建索引 x%」「索引过期」「数据不可用」。
- 各知识库的索引可以同时建立，进度事件带库 id。
- 搜索：一次查询所有有索引的知识库，结果按知识库分组（规范 8.2）：顶部是各库命中数，默认显示第一个有命中的库，点选切换；分面、分页只针对当前库。标签 id 是 `<库>|<路径>`，工作区版本升到 2，旧版的阅读进度自动迁移到 `cbeta|…`，旧布局不再还原。
- 图片协议 `sl` 的地址带库 id：`http://sl.localhost/<库>/<数据包内路径>`，允许 `figures/` 和 `a/` 下的图片。

**HTML 文章（`core/src/article.rs`）**

- 两种格式：`a/LZ/` 是 Trilium 导出（正文在 `div.ck-content`，标题在 `h1[data-trilium-h1]` 重复一次，跳过）；`a/ZB/` 有 `<meta author= library= catalog= period= book= name=>`，正文是带 id 的 `p`，部分文章有同目录下的配图（`src="a/69.jpg"`，相对文章所在目录）。
- 文章读成与卷相同的 `VolumeText`，**以段落代替行**：每个块（p、h1–h6、li、td 等）开始一个「行」，编号 `¶1`、`¶2`…；段落之间在 `text` 里加一个不计数的空格。因此定位、片段、高亮、跳转都直接复用；命中位置显示为「¶13 第1字」。
- HTML 只按白名单重建（段落、标题、列表、表格、粗体斜体、上下标、图片），脚本、样式、链接、事件都不会进入阅读区；图片路径不能跳出数据包。
- 索引文档的分面：`/bulei/` 取目录树里前两层文件夹，`/book/` 取 meta 的 book（没有则取所在文件夹），`/kind/` 取 meta 的 catalog，`/period/`、`/person/` 取 meta。
- 实测：乾隆大藏经 8095 篇，建索引约 6 秒（release）、158 MB；索达吉堪布全集 5242 篇，约 8 秒、102 MB。

## 10. 数据与目录布局

```
app_data/
  config.toml                 全局设置
  registry.db                 仓库注册、目录树设置、阅读历史、书签、收藏
  repos/<repo_id>/index/      该仓库的 Tantivy 索引（可删可重建）
  repos/<repo_id>/notes.db    仅自维护仓库：用户数据
```

原则：只读仓库只记录路径或引用，不复制、不修改源数据；所有衍生数据（索引）都可以随时删除重建；用户自己创作的数据（笔记）单独存放，便于备份与迁移。

  - 阅读区有两种版式：「段落」是附录 A.6 的结构化渲染（段落、偈颂、科判、表格、词条、图片、校注气泡、异文悬停、缺字），「原书行」是一行一行的纯文本；两者都支持命中高亮和跳行。版式选择存在前端本地。还不支持简体显示。
- **M2 标题快搜**（已完成，见 8.7）：双击 Shift 即时检索经、目次、卷和文章标题。
- **M3 本地目录适配器**：文件系统、增量索引、文档文本提取。
- **M4 自维护知识库**：Note 模型、编辑器、实时索引。
- **M5 Obsidian 与 Wikipedia**：Obsidian 作为 M3 的扩展，Wikipedia 单独调研。
- **M6 可选增强**：语义检索（本地嵌入模型加混合检索）、范围保存、搜索结果集管理。

每个阶段都应该是可独立使用的软件，避免走到后期才发现架构问题。

## 附录 A：CBETA bookcase 格式

来自实际样本（`samples/cbeta`）和对旧 Java 实现（cbeta-explorer 作者的 appxi-cbeta 库）的阅读。这些是靠样本很难发现的隐藏规则，新实现应逐条对照。

### A.1 读取与入口

- zip 根目录为 `Bookcase/CBETA/`，`index.xml` 等都在这一层；导航里的 `XML/T/T01/…` 是相对这一层的路径。
- zip 条目名：实测 2025.Q1 包的 85159 个条目**都没有 UTF-8 标志**；CBETA 自己的条目是 ASCII，用户加入的 `a/` 目录下 8773 个条目名是 **GBK**。新实现逐个条目读原始字节：是合法 UTF-8 就按 UTF-8，否则按 GBK（`source::decode_entry_name`）。不能用 zip 库默认的 CP437 解码。
- 压缩方式只有 deflate（8）和 stored（0），`zip` crate 只开 `deflate` 特性即可（默认特性带的 lzma 等 C 代码在 Windows GNU 工具链上编译失败）。
- 必须存在且不为空的 7 个文件：`advance_nav.xhtml`、`bookdata.txt`、`bulei_nav.xhtml`、`catalog.txt`、`menu_nav.xhtml`、`simple_nav.xhtml`、`spine.txt`，缺任一个就认为不是有效的 bookcase。
- 也支持已解压的目录，依次尝试根目录、`CBETA`、`Bookcase/CBETA`、`cbeta/Bookcase/CBETA` 下的 `index.xml`。
- **编码**：`catalog.txt` 是 UTF-8，`bookdata.txt` 是 UTF-16LE（带 BOM）。统一按 BOM 自动判断编码最稳妥。
- `index.xml`：指向 `catalog.txt`、`bookdata.txt`、`spine.txt`、`menu_nav.xhtml`，并带有版本号和日期。旧实现把日期折算成季度版本（1、2 月算上一年 Q4，3–5 月为 Q1，6–8 月为 Q2，9–11 月为 Q3，12 月为 Q4）用于缓存失效。
- `spine.txt`：列出所有卷文件及各卷起始行号（形如 `XML/T/T01/T01n0001_001.xml , 0001a01`），旧实现没有使用它，可用于校验。

### A.2 书目文件

- `catalog.txt` 每行按「, 」切成 8 段并去掉空白：藏经代码、部类、子类、册号、经号、卷数、经名、作译者。部类和子类拼成「部类/子类」（子类常为空）。作译者带朝代前缀，如「唐 慧菀述」。
- 经 ID 是藏经代码加经号，如 `T0004`、`A1267`。
- 经名可能带「(第N卷-第M卷)」后缀：解析出卷范围，并从经名中去掉。同一经 ID 出现多行时合并成一部经，每行把自己的卷范围映射到本行的册号（得到「卷号到册号」的表）。**卷范围只是提示，不是保证**：A1493 的名称写「第3卷-第12卷」（10 卷），但卷数栏是 9。以 toc 和文件实际存在为准。
- 卷文件路径可以直接构造：`XML/{藏经}/{藏经}{册}/{藏经}{册}n{经号}_{卷号，三位补零}.xml`。
- `bookdata.txt` 按「,」切成 5 段：藏经代码、数字、简称、全称、英文名。数字的含义未知，暂不使用。

### A.3 目录树

- `menu_nav.xhtml` 列出目录树。CBETA 官方是三棵：`simple_nav`（簡易）、`advance_nav`（進階）、`bulei_nav`（部類）。树 ID 取文件名去掉 `_nav.xhtml`。
- 用户的 bookcase 另加了两棵：`zhibei_nav`（索达吉堪布全集，5242 个叶子）和 `longzang_nav`（乾隆大藏经，8095 个链接节点），所有叶子都指向 `a/` 下的 HTML 文件（全部存在）。所以树的数量不固定，按 menu 列出的为准。
- `nav` 的 `default` 属性是**默认树的 ID**：`default="zhibei"` 即 `zhibei_nav.xhtml`。
- 所有 `*_nav.xhtml` 的顶层第一项都没有 `<li>` 包装。解析时把 `nav` 元素本身连同它的直接子 `li` 当作第一层即可自然解决。每个 `li` 先找 `span`（目录节点，子级在 `ol > li` 里），没有则找带 `href` 的子元素（叶子）。
- 叶子的链接直接指向卷文件（`XML/T/T01/T01n0004_001.xml`），文字形如「T0004 七佛父母姓字經」，**只指向该经的第 1 卷**。叶子按 `href` 的前缀分四种处理：
  - `XML/…`：取文字的第一个词（空格或全角空格之前，如 `T0004`）查 catalog。查不到且以小写字母结尾（如 `T0220a`）时，去掉字母查基础经，克隆一份，标题取整段文字，起点记为该链接。也就是说，nav 里的一个叶子可能只是某部大经的一段。
  - `toc/…`：用属性 `i` 作为经 ID，到 catalog 里查。
  - `a/…`：扩展库条目，元素是 `<a>`，属性 `i` 是 ID（如 `ZBzz005_001`、`LZa_1`），`a` 是作译者、`p` 是朝代（均逗号分隔，可缺），库名取路径第二段（`ZB`、`LZ`）。目标是 Trilium 导出的 HTML（正文在 `div.ck-content`，标题在 `<title data-trilium-title>`），同目录下有配图 `.jpg`（共 7226 张）。这类叶子没有 catalog 记录，M0a 只报告不解析；之后作为「HTML 文章」内容节点处理（每个文件一个节点，参与全文索引）。
  - `help/other/…` 及其他：以属性 `i` 或链接的哈希为 ID。实测 simple、advance、bulei 三棵树各有 303 个，都在「漢譯南傳大藏經」下，是 N 藏的说明、序和各册目录页（`.htm`），不对应经。
- 无链接的 `span` 节点：标题取属性 `t`，没有则清理文字。文件夹标题带机器码，如「01 阿含部類 T01-02,25,33 etc.」，清理规则：按空格切词，去掉以字母或等号开头的词、开头为数字的词，「etc.」按空白处理，以「／」分组。
- nav 的 `han-lang` 属性标明文字类型，默认繁体；用户加的两棵树是 `han-lang="hans"`（简体）。这意味着标题快搜和全文搜索都要考虑繁简互查。
- 用户加的两棵树里，顶层第一项**有** `<li>` 包装，与 CBETA 的不同；现有解析两种都能处理。
- **链接节点也可以有子级**：`longzang` 里有 `<li><a href="…/菩萨戒本.html">菩萨戒本</a><ol>…</ol></li>`（2 处，共 5 个子项），即「有内容且有子级」的节点。解析时带链接的 `li` 也要读它的 `ol`。样本 `samples/cbeta/longzang_nav_fragment.xhtml`。
- 实测（2025.Q1）：simple、advance 各 6137 个叶子，5834 个对应到经；bulei 5449 个叶子，5146 个对应到经，其中 15 个是大经的一段（克隆）。

### A.4 每部经的 toc 文件（经与卷的关联）

- 经的 toc 路径由 catalog 的经 ID 推出：`toc/{藏经代码}/{经ID}.xml`（如 `toc/T/T0004.xml`），位于 `Bookcase/CBETA/` 下。
- 里面有两个 nav：`nav type="juan"` 一定有，列出每卷的文件和起始锚点；`nav type="catalog"`（经内章节目录，嵌套的 `ol/li`）可有可无，T0004 就没有。
- 一部经的所有卷文件，等于这两个 nav 里全部链接去掉 `#` 之后的文件路径，去重并排序。
- **一卷可能分在两册**：同一卷号对应两个文件，如 `L130n1557_017` 和 `L131n1557_017`、`X39n0714_003` 和 `X40n0714_003`、`GA036n0037_002` 和 `GA037n0037_002`。catalog 里两行的卷范围在这一卷重叠（`(第1卷-第17卷)`、`(第17卷-第34卷)`），toc 两个文件都列。所以「卷号到册号」是一对多，卷文件要按（卷号，路径）去重，不能只按卷号。每个文件仍是一个文档。样本 `samples/cbeta/toc_X0714.xml`。
- toc 的 `juan` 列表不一定一卷一条：X0714 每卷分成「一上之一」「一上之二」等多条，指向同一文件的不同锚点。
- 实测（2025.Q1，4798 部经）：每部经都有 toc 文件，都至少有一个卷文件，toc 列出的卷文件全部存在。卷号可以有缺（A1267 没有卷十一，toc 也不列）。
- 锚点是 `p` 加行标记（`p0001c18` 即第 1 页 c 栏第 18 行），与卷 XML 里的 `lb n` 一致，可直接作为「转到」的定位。
- **章节目录里的顺序有语义，不能按锚点排序**：T0262 的「附文」锚点在第 198 页，却排在第 55 页与第 56 页的章节之间。章节可以嵌套（附文下有子项），也可以平铺；条目文字自带序号，如「1 序品」。
- 卷标题在 toc 里是「第一」「第二」，界面显示用「卷一」。
- 补缺：卷号不从 001 开始，或相邻两个卷号相差大于 1 时，旧实现补出缺的卷节点（类型为 title，即没有内容的占位），之后再用 catalog 的「卷号到册号」表补一遍。这些占位卷的文件可能并不存在，新实现用 zip 目录判断。
- 章节节点：当父节点还没有子节点、且与第一个子节点指向同一个文件时，子节点继承父节点的锚点。

- **不被任何经引用的卷文件**（实测 587 个）全部属于两套 catalog、bookdata、nav 里都没有登记的藏经：`LC`（呂澂佛學著作集，8 部 127 卷）和 `Y`（印順法師佛學著作集，44 部 460 卷）。它们有 `toc/LC/`、`toc/Y/` 文件和完整的卷 XML（授权声明是非商业使用），但 CBETA 自己的目录不显示。**决定：暂不收录**，不为它们生成节点，也不索引；`check` 把它们列为「未登记，忽略」。以后如果要收录，书目只能从 toc 和卷 XML 的 `teiHeader` 里取。
- **通用规则：菜单里有、但取不到真实内容的条目，保留在树里，解析时忽略即可**，不报错、不中断装配（例如链接指向的文件不存在、经号查不到、卷 XML 无法解析）。这种情况在用户自建的菜单里时有发生，`check` 负责把它们列出来供人工查看。

### A.5 作译者、朝代、典类

- 旧实现带一张人工整理的表，约 4800 部（经 ID 对应典类、标题、朝代、作译者）。典类分：经、律、论、经释、律释、论释、仪轨念诵法、传记、史、记录纪事、山志寺志、语录、序、目录、文献、音译、其他。分面中的「典类」「人物」「时域」就来自这张表。已转成 `data/bookinfo.json`（4826 条），转换脚本是 `tools/convert_bookinfo.py`。
- 表里没有的经才解析原始字符串：以空格切出朝代（长度小于 3，或属于乞伏秦、南北朝、宇文周），再用一组职责后缀（述、撰、譯、編修等）去掉职责得到人名，处理「等」「．」「、」分隔和括号注释。这种解析可能不准。
- 另有朝代表，给出各朝代的起止年份，并包含别称（如姚秦与後秦、北魏与元魏与後魏），可作为「时域」分面的归并和排序依据。该表在 Java 源码中，尚未导出。

### A.6 卷 XML（TEI P5 单卷版）的抽取规则

一个文件对应一卷，文件名形如 `T01n0004_001.xml`。样本见 `samples/cbeta/T01n0004_001.xml`，Python 参考实现见 `tools/ref_extract.py`。

| 元素 | 含义 | 抽取正文时 |
| --- | --- | --- |
| `teiHeader` | 经名、作译者、`idno`（藏经、册、经号）、缺字表 `charDecl` | 不入正文，作元数据 |
| `lb n="0159b05"` | 行标记，页码加栏加行号，是夹在正文中的空元素 | 记录文本偏移到行号的映射；只取 `ed` 等于藏经代码的那一套 |
| `pb n="0159b"` | 页栏分界 | 记录 |
| `p` | 段落，`xml:id` 末两位是段落在该行内的起始位置（不含标点，1 起算） | 记为锚点（`VolumeText::anchors`），也用来自动校验纯文本偏移 |
| `cb:juan`、`cb:jhead` | 卷头 | 入正文 |
| `cb:mulu` | 编者加的目录标签，原书不印 | **不入正文**（只用于大纲）。它的文字通常与紧随的 `head` 重复；实测去掉后段落锚点的不一致从 690 降到 175（T 藏抽样） |
| `app`、`lem`、`rdg` | 校勘：`lem` 是正文读法，`rdg` 是其他版本读法 | 取其中第一个 `lem`（没有时退到 `rdg`），忽略其余 `rdg` |
| `note` | 校勘注与脚注 | `place="inline"` 的是夹注，用全角括号包进正文；`type` 为 `cf1`、`orig`、`mod` 的跳过 |
| `g ref="#CB01979"` | 缺字引用，对应 `charDecl` | **一个缺字只输出一个字符**：单字的 normalized form > `mapping type="unicode"` > `mapping type="normal_unicode"` > PUA 码位；都没有时才用组字式或字名；找不到声明时输出 `@Declare@ID` |
| `space quantity="n"` | 空格 | 输出 n 个空格 |
| `cb:tt`（有无 `type="app"` 都一样） | 梵汉对照 | 只取 `zh-Hant` 的 `cb:t`，没有则取第一个 |
| `milestone`、`unclear` | 标记 | 整体跳过 |
| `byline` | 作译者署名行，位于正文开头 | 入正文 |
| 源文件中的换行与缩进 | 只是排版 | 丢弃，不当作正文 |

补充：

- `app type="star"` 是同一处异文的再次出现，里面也有 `lem`，要取。
- CBETA 修订过的读法，`lem` 的 `wit` 是 `【CB】`，大正藏原读法在 `rdg wit="【大】"`。默认取 `lem`，以后可做「原版读法」开关。
- **新式标点是 CBETA 加在原文上的一层，原书无标点**（`editorialDecl` 里有声明）。索引时去掉标点后，偏移就与原书的行内位置对应；多数行是 17 字，也有 16、15 字的行。
- **用段落锚点校验抽取**：`p` 的 `xml:id`（如 `pT09p0001a0501`）给出所在行和行内位置，等于免费的标准答案。`smart-library volumes <zip>` 对全部卷做这项检查：2025.Q1 共 231 万个锚点，98.8% 一致；去掉不收录的 Y 藏后不一致约 0.76%。
- **哪些字符不计入行内位置**（由锚点实测决定，不是猜的）：除原有标点外，`【】〖〗︵︶｀＇` 也不计入；`○ △ □ 〃 ※ ～ 〇`、制表符号（─│└┬ 等）、数字、拉丁字母都计入，保留在纯文本中。
- **缺字必须只占一个字符**：组字式（如 `[木*翕]`）占多个字符，会使行内位置偏移，也会给索引带来无意义的二字组。实测每个缺字声明都至少有一个 `mapping`（unicode、normal_unicode 或 PUA）。
- **悉昙字**（`SD-xxxx`）的「Character in the Siddham font」值（如 `一`、`乙`）是字体编码，不是文字，不能当正文；梵汉对照里一般取汉字那一侧。
- 已知不一致（约 0.76%，先记录，不影响 M0b）：CBETA 修订了文字的地方（`lem wit="【CB】"`），行内位置按大正藏原文（`rdg wit="【大】"`）计算，取 `lem` 时会差几个字；X 藏有大量行内位置超过行长的锚点（如一行约 20 字而位置是 55），可能是双行小字夹注另计，待查。
- `cb:docNumber`（如「No. 4 [No. 1(1), Nos. 2, 3]」）出现在正文最前，旧实现默认会把它包含在内，是否进入索引见第 12 节。
- **结构化渲染（已实现，`core/src/render.rs`）**：HTML 与文本抽取**共用同一次遍历**，正文字符按与 `plain` 完全相同的规则计数，所以检索命中（`plain` 偏移）可以直接在 HTML 里用 `<mark>` 高亮，`data-lb` 行标也正好落在 `lines` 所说的位置。2025.Q1 全部 21820 卷渲染后计数与抽取一致（`smart-library volumes <zip> --render`），约 3.4 ms/卷（抽取加渲染），共 108 万个校注标记、4361 张图（全部在 zip 中找到）。
- 渲染的结构映射：`cb:div` 到 div（class `t-类型`），`head` 到标题块，`byline`、`cb:juan`、`cb:docNumber`、`trailer` 到段，`lg`/`l` 到偈颂块与偈句（`caesura` 显示为空格，形成偈颂的两栏），`list`/`item` 到 ul/li，`table`/`row`/`cell` 到表格（`cols`、`rows` 合并），`entry`/`form`/`cb:def` 到词条，`cb:dialog`/`sp` 到问答，`hi`、`seg` 按 `rend`（bold、border、circle），`p cb:type="pre"`（科判）保留行内换行（`lb` 输出 `<br>`），`rend="text-right"` 右对齐。`style` 只保留以 em 为单位的 `margin-left`、`margin-right`、`text-indent`。
- 不计入正文、只在 HTML 里出现的：校注（`note` 带 `type`，`cf*` 除外）做成编号气泡；同一 `n` 的大正藏校注后紧跟 CBETA 修订校注时只显示修订版；`app` 的各读法（`wit` 加文字，以「；」分隔）放进 `title` 供悬停；梵汉对照另一侧放进 `title`（前端不用浏览器的单行提示，而是自绘浮层：正文读法在上，横线下面是其他版本，版本与文字两栏对齐）；`unclear` 显示为 ▆；`graphic` 显示图片。
- 图片：`url` 形如 `../figures/B/B06p0447_01.gif`，实际都在 bookcase 根目录的 `figures/` 下，取 `figures/` 之后的部分。桌面程序用自定义协议 `sl`（Windows 上是 `http://sl.localhost/figures/…`）从 zip 读取，只允许 `figures/` 下的文件。
- 缺字：正文与索引用单字符（见上），显示时若该字符是私用区码位（普通字体没有），改为显示组字式（如 `[木*翕]`），悉昙字显示转写，悬停显示缺字 ID。
- 其他：缺少 `xml:id` 的元素用「文档路径加选择器」的哈希生成稳定 ID；渲染结果按「文件名、修改时间、版本号」缓存。
