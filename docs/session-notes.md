# 设计会话纪要

这份文档把设计会话里的决策、依据和验证结果整理在一起，方便在新的开发环境里接手。规范本身见 `design-spec.md`，这里只记录「为什么这样定」。

## 1. 背景与约束

- 产品名定为 **Smart Library**（简写 `smart-library`）。此前只有工作名 `kb`。
- 目标：做一个轻量但搜索强大的本地知识库桌面软件，核心场景是收录多种《大藏经》文本，提供快速、精准的搜索，并可扩展到百科、Obsidian 库、本地资料目录和自维护笔记。
- 用户有一个旧项目 cbeta-explorer（Java + Solr + JavaFX），启动和搜索都很快，但 JavaFX WebView 能力不足，多年没有更新，想用新技术重做。
- 用户熟悉 Java，Rust 是新手；使用 Windows；用中文交流。
- 之前的会话只有 Chat 模式，**无法编译 Rust，也无法在大数据上测试**。M0a 的代码没有被编译过。现在转移到本地 Code 环境继续。

## 2. 决策记录

| 主题 | 结论 | 依据 |
| --- | --- | --- |
| 搜索引擎 | 嵌入式引擎，不用 Solr / Elasticsearch | Solr、ES 是分布式服务器，对单机几百 MB 文本过重；只需要 Lucene 层的能力 |
| 引擎选型 | Tantivy（Rust） | 体积小、启动快、支持短语、邻近、层级分面；Lucene 平均约快 1.5 倍（亚毫秒到毫秒级），对本规模无影响 |
| 分面 | Lucene 和 Tantivy 都原生支持分面 | 会话早期曾误以为 Lucene 不支持分面；Solr 只是把它做成了现成的请求参数 |
| 界面 | Tauri 2（系统 WebView） | 避开 Electron（约 100MB 起）、JCEF（约 200MB 级）和 JavaFX WebView（能力不足）；Node 只在开发时使用 |
| 语言 | Rust | 由 Tauri 与 Tantivy 决定；用户接受学习 Rust |
| 索引粒度 | 以「卷」为单位，一卷一个文档 | 整部大经作一个文档无助于排序和定位；卷是佛典自然的引用单位 |
| 节点模型 | 统一节点，不区分卷、文章、文件、笔记 | 它们结构相同，只差「有无内容、有无子级」；借鉴 Trilium 的 Everything is a Note |
| 仓库 | 每个仓库一个适配器、一个独立索引 | 规模差异大、分词策略可不同、便于单独重建 |
| 定位 | 搜索只返回命中的节点，命中位置在展示时由适配器实时解析得到 | 旧实现用 Solr 高亮片段回找位置，重复句无法区分 |
| 分词 | 沿用旧 Solr 的 text_aio（标准分词、全半角折叠、小写、CJK 二字组），并补充单字 | 混合文字实测没有问题；Tantivy 要自己写自定义分词器 |
| 标点 | 索引时忽略标点，保留位置映射 | CBETA 的标点是后加的一层，原书无标点；用户输入通常不带标点 |
| 匹配模式 | 宽松匹配为默认，另提供精确短语 | cbeta-explorer 的理念是不要求输入与原文一致 |
| 数据源 | 直接用官方 bookcase.zip，不维护衍生版本 | CBETA 持续更新，自己维护变异版本每次更新都要重新处理 |
| 开发顺序 | 先做 core 加命令行，再接界面 | 每一步都能独立验证 |

## 3. 对旧实现的验证结果

用 cbeta-explorer 实际测试得到：

- **单字查询可以命中**（搜「念」得 904 条结果，分面显示在左侧）。我曾按 Lucene 二字组过滤器的默认行为推测单字查不到，推测错误；旧 Solr 靠什么实现单字仍待核对。
- 用「他念摄之令常在像」搜索，只命中一卷，三段上下文来自同一卷的不同位置，高亮是分散的几块。说明默认是宽松匹配：二字组出现在同一卷内即可，不要求相邻，所以**这次测试不能证明可以跨标点**。
- 分面界面：部类、时域、人物、藏经、典类并列，部类是层级的且父级计数等于子级之和。截图在 `reference/`。

## 4. 对旧 Java 解析库的阅读（appxi-cbeta）

代码由用户上传，不放在本仓库。读到的规则都已写进规范附录 A，主要的隐藏细节有：

- 经与卷的关联靠每部经自己的 `toc/{藏经}/{经ID}.xml`，不是靠卷数推算，也不是靠 `spine.txt`（旧实现没用它）。
- `bookdata.txt` 是 UTF-16LE 带 BOM；`catalog.txt` 是 UTF-8。
- nav 的第一项没有 `li` 包装：把 `nav` 本身当第一项处理。
- nav 里的 `T0220a` 这类叶子是某部大经的一段，需要克隆基础经。
- 文件夹标题带机器码，需要清理。
- 卷 XML 里 `lb` 只取与藏经代码相同的 `ed`；缺字取 normalized form 优先；夹注要保留；校勘只取 `lem`。
- 一张人工整理的表（约 4800 部）提供典类、朝代、作译者，已导出为 `data/bookinfo.json`。

## 5. 样本带来的发现

- toc 里章节目录的顺序有语义：T0262 的「附文」锚点在第 198 页，却排在第 55 页与第 56 页的章节之间，不能按锚点排序。
- catalog 的卷范围不可靠：A1493 的名称写第 3 至 12 卷（10 卷），卷数栏却是 9。
- 段落 `xml:id` 的末两位是段落在该行内的起始位置，按不含标点的字数计，1 起算。标点是 CBETA 后加的一层（`editorialDecl` 有声明）。

## 5b. 在真实数据上的首次运行（Code 环境）

- 代码第一次编译就通过，22 个测试全部通过；唯一的问题是 `zip` 默认特性里的 lzma C 代码在 Windows GNU 工具链上 gcc 崩溃，改成只开 `deflate`。
- zip 条目名没有 UTF-8 标志，用户加入的 `a/` 目录是 GBK 文件名，补上了 GBK 回退。
- `check` 发现「一卷分两册」：原代码按卷号去重会丢掉其中一个文件（5 个）。改为按（卷号，路径）去重，catalog 的卷到册映射改成一对多。
- 其余 587 个未引用的卷文件属于 LC（呂澂）和 Y（印順）两套未登记藏经，属数据事实，不是代码问题。
- 用户加的 longzang 树里有 2 个「既是链接又有子级」的节点，原解析把它们当叶子，丢了 5 个子项；`NavNode::Leaf` 增加了 `children`。
- `menu_nav` 的 `default` 属性就是默认树 ID（`zhibei`），之前的样本来自用户改过的 bookcase。

## 5c. M0b：卷 XML 抽取

- `core/src/volume.rs`：quick-xml 读成小 DOM，再按 `ref_extract.py` 的规则遍历；同时记录 `p` 的 `xml:id` 锚点。
- **段落锚点是免费的标准答案**：`xml:id` 末尾是行号加行内位置。用它对全部卷做自动校验，发现并修正了参考提取器的几处规则（两边同步修改）：
  - `cb:mulu` 是编者加的目录标签，原书不印，跳过（之前和 `head` 重复输出）。
  - 缺字只输出一个字符：单字 normalized form > unicode 映射 > normal_unicode 映射 > PUA。之前用组字式 `[木*翕]`，占多个字符。
  - 悉昙字的「Siddham font」值是字体编码，不再当文字。
  - 不带 `type="app"` 的 `cb:tt` 之前整个被丢掉（丢了梵汉对照的汉字），现在同样取 `zh-Hant`。
  - 标点集合加入 `【】〖〗︵︶｀＇`；`○ 〃 ※ ～ 〇` 等经实测计入位置，保留。每组字符都是先试着去掉，再看锚点一致率升降来决定的。
- 结果：21820 卷全部解析成功，约 1.5 ms/卷（全部 32 秒）；Rust 与 Python 逐卷全部一致；锚点一致率 98.8%，剩余不一致主要是 X 藏的特殊计法和 CBETA 修订处（规范 A.6）。
- 用户决定：LC、Y 暂不收录；菜单里取不到真实内容的条目保留并忽略。

## 5d. M0c：分词、索引与搜索

- 分词器 `aio` 是纯函数（`analyzer.rs`），再包成 Tantivy 分词器；单字放在不带位置的 `body1` 字段，二字组和拉丁词放在带位置的 `body`。
- 第一次在真实数据上搜旧截图的「他念摄之令常在像」得到 0 条：查询是简体，CBETA 是繁体。于是加入一字对一字的繁简折叠（fast2s 的表，MIT，放在 `data/t2s.txt`）。之后结果与旧截图完全一致：只有《坐禪三昧經》卷一，經集部類 1。
- 宽松匹配定为「全部二字组都要出现」；同时规定查询里的空格分隔关键词（`比丘 他念`），否则会产生跨关键词的二字组。
- Git Bash 会把以 `/` 开头的参数改写成 Windows 路径，所以范围和分面下钻也接受不带前导 `/` 的写法（`bulei/阿含部類`）。
- Tantivy 不允许同一个分面收集器里既有父分面又有子分面，下钻用第二个收集器。
- 旧界面「念」904 条与新索引 18407 卷不可比：旧的文档粒度看来是章节。

## 5e. M1 界面骨架

- 用户选定 Svelte。`app/` 用 Vite + Svelte 5（runes）+ Tauri 2，Rust 部分 `app/src-tauri` 是 workspace 成员。
- 只用 GNU 工具链也能编译 Tauri；图标用 PIL 画一张源图，再用 `tauri icon` 生成。
- core 新增 `VolumeText::line_spans()`：把带标点的文本切成原书行；两行之间的标点归上一行，只有「『（等开头符号归下一行。
- 默认打开「簡易目錄」而不是 menu 的 `default`（zhibei），因为用户加的两棵树的 `a/` 内容还不能读。
- 实测（debug 版）：界面内建索引约 4 分钟（release 命令行约 43 秒）；「他念摄之令常在像」17 ms，点片段跳到 0272b10 并高亮跨行的「攝之令」；精确短语「如是我聞」1645 卷，点「般若部類」分面后 115 卷。

## 5f. 结构化阅读

- 用户提出三点：阅读区要多标签页（停靠、浮动、进度还原，每个文档只开一个）；知识库要能右键绑定，CBETA 三棵树只绑一棵（默认 bulei），自加的树可同时绑定；先做结构化阅读。
- 关键设计：HTML 渲染与文本抽取共用一次遍历，正文按 `plain` 的规则计数，因此搜索命中直接用 `plain` 偏移在 HTML 里高亮，不需要第二套映射。全部 21820 卷校验计数一致。
- 先统计了全部卷正文用到的元素（`caesura`、词条、问答、科判 `p cb:type="pre"` 等），再定映射。
- 图片在 bookcase 根目录的 `figures/`，用 Tauri 自定义协议 `sl` 从 zip 读取。
- 在程序里看过：法華經卷一（序、校注气泡、偈颂两栏）、B0009（书法图片）、G2259（科判框线）、太虛全書（跨行短语高亮）。

## 5g. 多标签阅读

- 用户选定：一卷一个标签；浮动既要窗口内面板也要独立窗口。
- 用 dockview-core 8：它的 ES 模块不带 CSS，从 UMD 版抽出到 `app/src/vendor/dockview.css`。
- 弹出窗口用 Tauri 多窗口而不是 dockview 自带的 `window.open`，因为后者要求同一 JS 上下文；主窗口独占 `workspace.json`，弹出窗口用事件汇报，避免两个窗口同时写文件。
- 进度按卷记录屏幕顶部的行号而不是像素，版式切换、字号变化后仍然准确。
- 验证中发现并修正：浮动面板默认太小；英文的 Maximize 菜单项去掉；Vite 热更新偶尔提供旧模块（需 touch 后刷新）。
- 重启验证时发现：此前 bookcase 路径来自环境变量、从未保存，所以重启后出现首次设置页面；输入路径后保存，工作区随即完整还原。

## 5h. 知识库绑定与 HTML 文章

- 先把 `a/` 下的 HTML 接入：两种格式（LZ 是 Trilium 导出，ZB 有 meta 元数据和配图）。文章读成以段落为「行」的 `VolumeText`，搜索、定位、高亮、跳转全部复用，不用为文章另写一套。
- 判断「同一份数据」不写死文件名，而是看叶子指向：`XML/` 为 CBETA，`a/<代码>/` 为各自的知识库。在真实数据上分类正确。
- 索引构建改为通用：适配器产生 `IndexDoc`，`search::build_index` 写入 Tantivy。
- 程序里验证过：旧设置自动迁移为部類目錄并沿用旧索引；右键空白处绑定；对话框单选 CBETA 树、多选两个自加库；两个库同时建索引；「如是我闻」跨库命中（部類 1645、索达吉 61、乾隆 793）；切换到乾隆、打开文章跳到 ¶13；索达吉文章的配图从 zip 显示；更换为簡易目錄后目录随即刷新、索引保留。
- 未用自动化验证：解除绑定（系统确认框无法用自动化点击），需手动试。

## 5i. 标题快搜（M2）

- 用户给的参照：IDEA 的 Search Everywhere（双击 Shift，上方标签切换范围，只能单选）和 cbeta-explorer 的快捷检索（细到序、品、卷、经）。用户的考虑是：有时明确要找一个东西，有时只是想探索。
- 用户定义了「知识库」：目录树的根节点就是知识库，知识库也只出现在根节点（已写进规范第 2 节和 CLAUDE.md）。快搜的范围标签因此就是各知识库。
- 不做前缀结构：部類目錄约 32 万条，线性扫描折叠后的字符串只要几毫秒，比维护前缀树简单；规模大的仓库（Wikipedia）以后再用 FST。
- 第一版条目里的经名、作译者每条都复制一份，改为每部经一个共用的组。
- 排序调整的依据：搜「金刚经」时，标题正好是「金剛經」的目次（多在语录、音义里）原先排在以「金剛經」开头的经前面，不合找经的习惯，所以「以关键词开头」这一档里经优先，完全相同只作为档内的次要依据。
- 注意：「法華」不是「妙法蓮華經」的连续子串，按子串匹配找不到；这类简称以后可以靠别名（规范第 4 节的 `aliases`）解决。
- 用户提出：快搜框要能粘贴 CBETA 的「复制为引用」文字直接转到经文（cbeta-explorer 已支持）。实测用户给的例子，引用写 `p. 269c29` 是卷首，引文在 276a07，所以有「…」引文时在卷内按短语找它，跳到引文的行并高亮；卷由 `spine.txt` 的起始行决定。
- 用户补充：cbeta-explorer 在快捷检索里输入 `#` 是 CBETA 专用的转到命令（7 种格式：册号加经号、经号加行、引用格式；经号加卷），只输入 `#` 时列出格式说明；粘贴引用时提取特征拼成 `#` 命令。照此实现，粘贴后引文另外保留，仍用于跳行和高亮。
- 只给经号和行（没有册号）时，一部经跨多册的页码会重新开始，所以选卷时遇到页码变小就认为进入了下一册，取第一个能容纳该行的卷。
- 修正：弹窗是纵向 flex，结果列表撑满时标签栏被压扁，标签栏和输入行改为不收缩。
- 已知：中文输入法常用 Shift 切换中英文，快速连按两次也会打开快搜（IDEA 也是这样）。

## 5j. 阅读区与目录树的改进

- 用户提出：目录树层级深时标题显示不全（固定宽度）→ 加可拖动分隔条；阅读标签要能定位到目录树 → 标签右键和标题栏 ⌖；切换标签回到顶部 → 查明是 dockview 把隐藏标签移出页面导致滚动归零，并没有重新载入，改为记住并放回滚动位置；异文提示改为对齐的浮层（参照 cbeta-explorer）。
- 编注的显示方式随后实现（规范 A.6 末尾）：用户指出数字标和异文悬停同时出现是多余的，又指出 cbeta-explorer 的「✱标」与现在的数字标作用相同、而且序号有用，所以「✱标」改为沿用数字标；另加「无」给只想读正文的人。实现上渲染时同时保留原编注和 CBETA 编注，切换只换样式。

## 5k. 可编辑的文件夹库（讨论结论，未实现）

- 起因：用户用过 Obsidian（目录 + md，可用 git 备份）和 Trilium（Everything is a Note，但只能用数据库）。本程序现有的外部文件夹只读、内部库用 SQLite 可编辑，想在不大改的前提下让文件夹库也能编辑 md、脑图、白板。
- 结论：可行，编辑器与存储无关，只需替换存取层。细则见规范 6.5。
- 用户的决定：
  1. 元数据放库内 `.smart-library/` 侧车（为了随 git 备份）。
  2. 不与其他笔记软件混用（原因：Obsidian 等软件在导入藏经、文集形成的海量文件上搜索和性能不行），所以不追求 Markdown 往返保真；对其他使用者，由挂载时的确认对话框告知规则和风险，该确认是只读变读写的必经步骤。
  3. 文件夹节点和只读库的节点禁用上移 / 下移。
  4. 本地文件重命名用严格的文件名约束，并显示「本地文件名限制」提示。
- 我补充的两点，用户同意：读写开关存本机而不放侧车（防止 clone 后绕过确认）；只读库的元数据仍留应用数据，不往只读库里写任何东西。
- 风险备忘：Milkdown 保存可能规范化 Markdown，所以只在内容真的改了才写盘；外部修改只在保存前比对修改时间。

## 5l. 整段异文（某版本整品缺）的渲染

- 用户发现 T16n0663_004（T0663 卷四）：整品正文上任意字符悬停都出 title，DevTools 显示整品被包在一个 `span.app.v` 里，`title` 是整段正文（`【大】金光明經囑累品第十九…；【明】（無）`）。数据里 `app n="0358001"` 的 `lem` 是整品（明藏缺此品）。
- 原因：`app` 的读法一律按行内异文包进 span，`title` 由各读法的全文拼成。
- 决定：`lem`/`rdg` 含块级元素时不包 span，直接把该读法按原结构渲染；同一 `n` 的编注（这首是「〔金光…而去〕一品四百二十八字－【明】」）照常显示，在着色方式里就是没有着色文字的编注点（✱）。见规范 A.6「不计入正文、只在 HTML 里出现的」。

## 5o. 阅读器字重档位

- 用户想给阅读器加一个「整体字更粗」的设置：正文变粗，原本用 `<b>`/`font-weight` 的强调相对更粗。CSS 没有相对字重（`font-weight` 没有 rem 那样的基数）。先做一个测试页，在本机 WebView2（Chromium 157）上验证：
  - `font-weight: calc(400 + 100)` 是支持的，算出来 500；变量派生 `calc(var(--w) * 1.25)` 也可以。
  - 同名自我引用 `--w: calc(var(--w) * 1.3)` 构成循环，计算值无效；要从祖先的基数派生到另一个变量名。
  - 浏览器默认 `<b>`/`<strong>` 用的 `bolder` 按固定阶梯走：400→700、500→700、600→900、700→900，600 以上饱和。实测基准 600 时正文和强调完全一样粗，强调被吃掉，所以不能用 `bolder`。
  - 真正的限制在字体：宋体只有「常规 / 合成粗」两档（约 550 以下都是常规，约 580 以上都是同一个合成粗）；微软雅黑实测 4 档（≤340 细、350–490 常规、500–640 中间、≥650 粗）。连续滑杆在宋体上大部分区间没有反应。
  - `-webkit-text-stroke-width` 用 em 写会随字号缩放，是加法的假粗，但能保证任意字体都有档位差别，而且不改变强调与正文的权重差；0.012–0.024em 在 19px 下观感可用，0.04em 开始糊。
- 决定：设置项「字重」三档（标准 / 稍粗 / 加粗），不是滑杆。`settings.svelte.js` 的 `WEIGHTS` 表给出每档的正文和强调字重，以及正文 / 强调的描边宽度（em）。正文用 `--reader-weight`，强调用 `--reader-strong-weight`；`b`、`strong`、`.head`、`.juan`、CBETA 粗体读法统一走强调档，覆盖浏览器的 `bolder`。稍粗档靠 500（雅黑有的档位）加 0.012em 描边（宋体这类两字面字体）同时生效；加粗档正文 650，强调 900 另加 0.024em 描边，以免字体到顶后强调和正文一样粗。只作用于阅读器和词典详情，笔记编辑器不跟随。

## 5p. 标签菜单样式、标签提示、目录树工具栏

- 阅读器标签的提示最后一行原来写成「目录：…」，用户要求去掉前缀，直接显示目录树路径（`workspace.svelte.js` 的 `ontreepath` 回调）。

## 5q. 词典导入

- 用户指出：查词典依赖的 `.words` 是旧程序内部格式，市面上没有现成词库，用户无法导入。要求支持早期词典软件的三种来源：① `.idx` + `.dict`（StarDict）；② `.mdx` / `.mdx` + `.mdd`；③ TXT（按旧 Java `DictFileTxt` 的规则）。旧代码在 `C:\Devx\appxi-dictionary-api`，样本在 `C:\Devx\appxi-dictionary.dd\zzzz3p`；用户还说明了 `.words` 的设计：标题集中放、mmap 扫描；词义按哈希去重、多个标题指向同一份词义；生成时自动补小写 / 简体 / 繁体变体，标题也去重。
- 旧的 Java `DictionaryBuilder` 是生成器的依据：标题区记录 `entry_size(17+标题)`、`pid`、`type`、`content_mark`、`title_len`；词义区是 `i32` 长度加压缩字节；标题和词义内容各自去重；变体追加在原条目之后。Rust 版（`core/src/dict_build.rs`）保持同样的布局，但把词义去重从 Java 的 32 位 `String.hashCode` 换成 128 位指纹，避免碰撞把不同词义接到一起。
- 两种真实 MDX 都标着 `Encrypted="2"`（键块信息加密）。旧 Java 的 `_mdx_decrypt` 不是 Salsa20，而是 `RIPEMD-128(块[4..8] + 0x3695)` 派生密钥后逐字节做 `swap_nibble(c) ^ 前一个密文字节 ^ 序号 ^ 密钥`；按这个实现后在两个真实 MDX 上都能完整读出 124,821 / 93,486 条。另有一个解析细节：头部的五个数字（键块数、条目数、键块信息解压大小、键块信息大小、键块大小）后面还有 4 字节 Adler32，Java 的 `num_bytes = 8*5+4` 算的正是这 44 字节；少读这 4 字节会从错误的位置取键块信息。
- StarDict 用 `sametypesequence=m` 的藏汉大辞典（53,379 条）验证；MDD 的头部可能 `Encoding=""` 但键块信息仍是 UTF-16LE，所以解析器先按头部宽度试，失败再换另一种宽度，并以“正好消费完整个信息块”为准。
- 用户点验时发现直接选 `.idx` 导入会报「文件不完整」，而选 `.dict` 能导入。原因是 `star_dict_base` 把 `.idx` 也按 5 个字符截断（`.dict` 才是 5 个），`藏汉大辞典1.idx` 被截成 `藏汉大辞典`，找不到同名 `.dict`。改为按每个后缀的实际长度截断（`.dict.dz`/`.idx.gz`/`.dict`/`.idx`/`.ifo`），并保留原文件名大小写；补了 `.idx`、`.dict` 任一文件导入的回归测试。目录扫描也改成按字典主干只选一个来源（`.ifo` → `.idx` → `.idx.gz` → `.dict` → `.dict.dz`），修掉了只有 `.idx.gz` + `.dict` 时两个文件都被跳过、以及 `.ifo` + `.dict.dz` 时重复导入的问题。
- 简繁变体：简体沿用 `data/t2s.txt` + `data/variants.txt`；繁体是逐字反查，优先标准字形。发现 `t2s.txt` 里也有 `彿/髴 -> 佛` 这类异体折叠，直接反查会把「佛」变成「彿」，所以对 佛、后、干、台、只、系、余、谷、斗、松、胡、云、里、面 这些一字多形或本身合法的字保持原样。旧 Java 的 `ChineseConvertors.toHant` 是词语级转换，这里只能近似，已在 design-spec 记为限制。
- 输出放在 `<数据目录>/dicts/`，自动加入 `dicts.json` 的 `paths`；应用导入前先丢掉 `DictManager`，释放 Windows 上对旧 `.words` 的 mmap，才能覆盖同名文件。CLI 的导入输出默认是仓库下的 `app_data/dicts`，方便先跑通。
- 不提交真实词典；`samples/dict/` 是 `tools/make_dict_samples.py` 生成的小样本（含加密键块信息的 MDX、MDD 图片和 StarDict）。

## 5r. 本地文件夹的回收站与恢复

- 用户指出：读写本地文件夹的删除只做到「移进 `.smart-library/trash`」，没有恢复，只有清空。要求补恢复。
- 旧回收站的文件名是 `<时间>-<名字>`，只留了最后一段名字，原来的上级文件夹丢了，无法原位恢复。两个做法比较：把原相对路径编码进文件名，或换成分批目录；最后选在旁边加一个 `.smart-library/trash.json` 索引，记录每个条目的 `entry`（回收站里的名字）、`rel`（原相对路径）、`kind`（`file` / `dir` / `picture`）和删除时间。索引丢了或坏了也不影响数据：列回收站时以目录里实际存在的文件为准，没有索引的旧条目按 `<时间>-<名>` 还原名字、恢复到顶层。索引和回收站一起被「清理缓存」删除。
- 图片不单独列出，也不按「同一批删除」分组恢复，而是在恢复文件或文件夹后读出其中的 Markdown / 脑图 / 白板引用（`attach::refs`），把还在回收站里的对应图片移回 `.smart-library/attachments/…`。这样即使索引里的批次信息不全，只要图片还在回收站就能带回来；仍然被别的笔记引用的图片本来就不在回收站，跳过即可。
- 原位置有同名文件夹时逐层合并进去（用户先恢复笔记里的文件、再恢复文件夹时，不应多出一个 `b 2`）；只有同名文件自动用 `名字 2`、`名字 3`（保留后缀），不覆盖也不弹窗；恢复前先建好上级文件夹。恢复的文件记入「待索引」；属性在删除时已经从侧车移除，恢复不还原属性（要保留得改删除流程，先不做）。
- 入口放在目录树右键知识库 →「回收站…」，因为回收站是按知识库的（每个读写文件夹一个）；删除确认框改成提示可以去那里恢复。内部知识库的笔记不进这个回收站；它们后来用删除快照做了自己的回收站，见 5s。

## 5s. 内部库的删除与恢复（借用快照）

- 用户提出：内部库删除后不能恢复；既然快照已经有「临时 AI / 手动」的 kind，可以再加一个 `deleted` 标记，删除时建快照，回收站只列这种快照，恢复时原路创建、同名加数字。
- 采用这个思路，但删除的是一棵子树：快照内容不是单篇的 Markdown，而是整棵树的 JSON（`notes::DeletedTree`，每个节点带原 id、标题、内容、类型、位置、子节点），另外记**标题路径**（`path`：从顶层到直接上级的标题，用 `folders_of` 取，不记 id）。这样一次删除操作在回收站里是一行，恢复也是整棵回来；`snapshots.list` 过滤掉 `deleted`，不会混进文档快照对话框。
- 恢复位置最后定为「按标题路径重建」（用户提出）：删除时记下节点所在位置的标题组合；恢复时逐级看，现在的树里有同名节点就重用它，没有就新建一个同名的空笔记，然后在最终上级下新建这一篇。只有恢复的这一篇本身碰到同名时才加数字（`标题 2`），它下面的子节点按原样新建。回收站里的其他条目完全不动：只恢复 Chapter1 不会让 Book 的条目消失，也不会把 Note1 带回来；以后恢复 Book 时，因为位置上的 `Book` 已经存在，会得到 `Book 2` 和它下面的 Note1。
- 中间试过两版都放弃了：第一版按快照根 id 找到上级并恢复整棵，用户指出「只点一次恢复，却把 Note1 也恢复了」；第二版只恢复上级本身、把上级的其他子节点拆成新回收站条目，用户指出 Book 的条目不该消失、不该自动变成多个条目，并建议改成按显示名（标题）重建。现在按第三版实现。
- id 处理：逐个节点判断——原 id 空闲就用 `create_with_id` 沿用（日记的固定日期 id `YYYYMMDD` 和按 id 记的书签能重新对上），被占用就换新 id。父子关系按实际建出的 id 连，所以部分沿用、部分换新也安全；id 冲突不覆盖。旧版快照没有标题路径时按原来的上级 / 祖先 id 兜底。
- 图片：内部库的图片按引用计数，删除笔记会把计数减到 0，每日清理 24 小时后删文件。为让回收站里的笔记还能恢复图片，删除时把子树引用的图片名写进 `notes.db` 的 `trash_refs`（按快照 id），`sweep_pictures` 跳过这些名字；恢复或永久删除快照时释放。这样回收站没清理之前图片跟着留着。
- 永久删除 / 清空回收站走 `delete_snapshot` / `purge_deleted_notes`，会先释放图片保留。删除内部知识库时一并删掉该库的删除快照（`SnapshotStore::remove_lib`）；外部库解除绑定时不删（和属性一样，重新绑定后还在）。
- 入口沿用知识库右键「回收站…」，内部库打开 `NotesTrashDialog.svelte`。恢复单条时在目录树里展开并选中恢复出的笔记（`showNew`），全部恢复时刷新目录树。
- 属性：用户问「删除时能不能连属性一起保存」。能。删除时把子树里每个节点的 `props.db` 维度、别名和 `marks.db` 的节点标签按旧 id 放进快照的 `meta`（`DeletedMeta`）；`NotesStore::restore_deleted` 返回旧 id → 新 id 的对应，命令据此写回。被显式设为空的维度（`Dims` 里值为空表）也照原样写回。删除时同时移除 `props.db` 的属性和 `marks.db` 的节点标签记录（快照里已有），恢复时按新 id 重建，避免旧的悬空标签和新标签并存。旧版本生成的删除快照没有 `meta`，恢复不了属性。
- 目录树：恢复出的节点在树里默认折叠。原先的展开状态按索引路径保存，恢复出的节点落到旧节点相同的路径时会被当成展开，但它的子节点从没读过，于是显示成展开却是空的；`showNew` 现在清掉该路径及其子路径的展开状态，等用户点开再读。
